# study-aid — v0.2 Iteration Plan

Builds on the completed MVP (`mvp-implement-plan.md`, all 8 epics done). This iteration adds persistent quiz storage, a dashboard to browse past quizzes, and closes two UX gaps in the upload/generation flow where the app gives no feedback while it's working.

> Status key: `[ ]` Not started · `[~]` In progress · `[x]` Done

---

## Epic 1: Persistent Quiz Storage (SQLite)

**Goal:** Replace the in-memory, 2-hour-TTL session store with a SQLite-backed store so generated quizzes and attempts survive server restarts and don't expire. One running app instance is assumed to belong to one user — no per-user/device scoping in this iteration (that comes later, alongside login).

**Status:** `[x]` Done

### Stories

- [x] **S1.1** Design the SQLite schema — a single `quizzes` table (`id`, `source_text`, `truncated`, `quiz` JSON, `attempts` JSON, `failure_counts` JSON, `created_at`), deliberately shaped to match the current in-memory session dict closely, to minimize migration risk
- [x] **S1.2** Create `db.py` with `init_db()`, `create_quiz() -> dict`, `get_quiz(quiz_id) -> dict | None`, `save_quiz(quiz: dict) -> None` — function names/shapes mirror `session_store.py` so most existing call sites change minimally
- [x] **S1.3** Wire `init_db()` into app startup; remove the old `_cleanup_loop` background task (no longer needed — nothing expires anymore)
- [x] **S1.4** Migrate every route in `main.py` off `session_store` onto `db.py` — replace `create_session()`/`get_session()` calls, and add explicit `save_quiz()` calls at each point a quiz/attempt is currently mutated in place (e.g. after `session["quiz"] = ...`, `attempt["answers"][qid] = ...`)
- [x] **S1.5** Delete `session_store.py` and the 2-hour TTL/expiry logic; replace the expiry-flash-message flow (`_session_expired_redirect`) with a "quiz not found" message, since quizzes no longer expire — they just might not exist
- [x] **S1.6** Update existing test fixtures that reach into `session_store._store` directly to work against the new SQLite-backed store (a temp or `:memory:` database per test)

### Testing

- [x] Unit: `create_quiz()` returns a row with an empty quiz, empty attempts, current timestamp
- [x] Unit: `save_quiz()` persists a mutated quiz dict correctly; `get_quiz()` reads back the identical shape
- [x] Unit: `get_quiz()` returns `None` for an unknown id
- [x] Integration: full existing test suite (107 tests, after removing 12 obsolete session_store-internals tests and adding 6 new db.py unit tests) passes against the new store with updated fixtures
- [x] Integration: a quiz's data — including a completed attempt — survives a simulated server restart (fresh `get_quiz()` read, not the same in-memory object)

### Demo

Generate a quiz, complete a practice attempt, then restart the server process. Reload the quiz's URL — the quiz and the completed attempt are still there, unlike today.

### Implementation note (not anticipated in the original stories)

The old in-memory store used a `session["_generating"]` dict flag to prevent overlapping HTMX polls from triggering duplicate Claude calls, which worked because every `get_session()` call returned the *same* shared dict object. SQLite's `get_quiz()` returns a *fresh* dict reconstructed from a `SELECT` on every call, so that check-then-set pattern would silently stop working (two concurrent polls could both see `_generating` as unset and both call Claude). Fixed by moving the lock to a plain in-memory `set[str]` in `main.py` (`_generating`), kept deliberately unpersisted — it's a per-process concurrency guard, not durable quiz data, and if the server restarts mid-generation the attempt is simply retried.

## Epic 2: Quiz Dashboard

**Goal:** A landing point where a user can see every quiz they've generated on this instance and jump back into practicing or evaluating any of them, without needing to have bookmarked the specific URL.

**Status:** `[x]` Done

### Stories

- [x] **S2.1** Add `list_quizzes() -> list[dict]` to `db.py` — quiz summaries (id, source text preview, created_at, latest attempt's mode/score if any), ordered most-recent-first
- [x] **S2.2** Implement `GET /dashboard` — renders `dashboard.html` with the list from S2.1
- [x] **S2.3** Create `templates/dashboard.html` — a card per quiz: short source-text preview, creation date, latest score (or "not yet attempted"), and a link into it
- [x] **S2.4** Handle the empty state — no quizzes yet, with a clear call-to-action back to `/` to create one
- [x] **S2.5** Add a nav link to `/dashboard` from the base template so it's discoverable from anywhere in the app

### Testing

- [x] Unit: `list_quizzes()` returns quizzes ordered most-recent-first
- [x] Integration: `GET /dashboard` with no quizzes shows the empty state
- [x] Integration: `GET /dashboard` with several quizzes shows all of them with correct previews/scores
- [x] Integration: clicking through from the dashboard into a quiz correctly resumes/starts practice mode

### Demo

Generate two or three quizzes from different documents, complete a practice attempt on one. Visit `/dashboard`, see all of them listed with the completed one showing its score, and click through to retake one.

### Implementation note (not anticipated in the original stories)

"A link into it" (S2.3) needed a concrete routing decision per quiz state, since a single destination doesn't fit all of them: **not yet generated** → `/generating/{id}` (resumes the spinner, which retries generation); **generated but never attempted** → `/quiz/{id}` (starts practice); **attempt in progress** → `/quiz/{id}?mode={latest_mode}`; **attempt completed** → `/results/{id}` (shows the score, with its own Practice Again / Evaluation Mode buttons, rather than silently starting a new attempt). This logic lives in the `/dashboard` route in `main.py`, not in `db.py`'s `list_quizzes()`, to keep the DB layer free of URL/routing concerns.

## Epic 3: Ingest & Generation UX Feedback

**Goal:** Users get clear visual feedback at the two points that currently feel like the app has frozen — while a file is uploading/parsing, and while Claude is generating the quiz.

**Status:** `[x]` Done

### Stories

- [x] **S3.1** Add an upload-status indicator to `templates/index.html` — a small script shows a spinner + "Uploading and processing your file…" and disables the submit button on form submit, without intercepting the actual browser form submission (no backend changes)
- [x] **S3.2** Update `templates/generating.html` copy to explicitly name Claude and set a time expectation (e.g. "Talking to Claude… Claude is reading through your material and writing quiz questions. This usually takes 10–30 seconds.")

### Testing

- [x] Integration/manual: submitting the upload form shows the status indicator immediately — verified structurally (form/button/status element wiring, event listener present, no `preventDefault()`); could not visually confirm in a live browser, as the Claude-in-Chrome extension wasn't connected in this environment
- [x] Integration: `generating.html` renders the updated copy (text-presence check)

### Demo

Upload a document and narrate what's visible at each step — the "Uploading…" indicator appears immediately on submit, then the generating page clearly states Claude is working and roughly how long it'll take.

### Implementation note (small deviation from the original story text)

The upload-status message says "Uploading and processing your material…" rather than "...your file…" — the form also accepts pasted text with no file involved, and "your file" would be inaccurate for that path. Same spinner/disable-button mechanism either way.

### Follow-up fix (found via user testing after initial implementation)

S3.1's submit-time spinner wasn't the actual gap the user hit — on localhost the `/ingest` round-trip is ~10ms, too fast to perceive before the browser navigates to `/generating/{id}`. The real gap was upstream of that: after picking a file, the drop-zone box still read "Click to upload" with no indication a file had actually been selected, leaving no way to tell it was safe to click "Generate Quiz". Fixed by adding a `change` listener on the file input that swaps the label text to "Selected: {filename}" and highlights the drop-zone border/background, giving immediate confirmation at selection time rather than relying on the submit-time spinner being visible.
